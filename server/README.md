# Сервер Citavuk

Go-сервис: аккаунты, синхронизация между устройствами и перевод.

Заменяет ту часть Python-бэкенда, которая отвечает за перевод, и добавляет то,
чего раньше не было вовсе, — учётные записи и синхронизацию. Разбор слов
(CLASSLA), новости, извлечение статей и синтез речи пока остаются на прежнем
сервисе: запросы к ним проксируются, поэтому у приложения один адрес сервера.

## Что где лежит

```text
server/
├── cmd/citavukd/          точка входа
├── internal/
│   ├── config/            чтение .env и переменных окружения
│   ├── store/             PostgreSQL: пользователи, сессии, синхронизация, кеш
│   │   └── migrations/    SQL-миграции, применяются на старте
│   ├── auth/              пароли, сессии, Google ID token и Yandex OAuth
│   ├── mailer/            транзакционные письма через Resend
│   ├── translate/         DeepL, запасной провайдер, выравнивание слова
│   └── api/               HTTP: маршруты, middleware, обработчики
└── deploy/                unit systemd, vhost nginx, скрипт выкатки
```

## Запуск локально

```powershell
cd C:\citavuk\server
go run ./cmd/citavukd -env ../.env
```

Сервер слушает `127.0.0.1:8090`, применяет миграции на старте и проверяет
готовность по `GET /health`.

Тесты, включая интеграционные с настоящей базой:

```powershell
go test ./...
```

Тесты, которым нужна база, берут строку подключения из
`CITAVUK_TEST_DATABASE_URL`, а если её нет — из `.env` в корне репозитория.
Без доступной базы они пропускаются, а не падают.

## Настройки

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` (или `DB_URL`) | — | PostgreSQL, обязательна |
| `REDIS_URL` | — | необязательный Redis/Valkey для L1-кеша и общего rate limit |
| `CITAVUK_REDIS_PREFIX` | `citavuk` | пространство ключей в общем Redis |
| `CITAVUK_REDIS_CACHE_TTL` | `24h` | TTL горячего кеша переводов |
| `DEEPL_API_KEY` | — | ключ DeepL; суффикс `:fx` означает free-план и другой хост |

| `CITAVUK_UPSTREAM` | HF Space | куда проксировать разбор, новости и аудио |

| `CITAVUK_TRUST_PROXY` | `false` | читать `X-Forwarded-For`; включать только за nginx |

| `CITAVUK_EMAIL_VERIFICATION_TTL` | `24h` | срок жизни ссылки подтверждения |

## Методы

### Аккаунт

```text
GET  /v1/auth/providers
POST /v1/auth/register               {email, password, displayName, device}
POST /v1/auth/verify-email           {token}
POST /v1/auth/resend-verification    {email}
POST /v1/auth/login                  {email, password, device}
POST /v1/auth/google                 {idToken, device}
POST /v1/auth/google/desktop         {code, codeVerifier, redirectUri, device}
POST /v1/auth/yandex/start           {returnTarget, returnUrl?, device}
GET  /v1/auth/yandex/callback
POST /v1/auth/yandex/complete        {code}
POST /v1/auth/logout
GET  /v1/auth/me
POST /v1/auth/password   {currentPassword, newPassword}
```

Регистрация по почте отвечает `202 Accepted` и **не выдаёт сессию**. Пользователь
может войти только после перехода по одноразовой ссылке из письма. Повторный
запрос письма отвечает одинаково для отсутствующего, уже подтверждённого и
неподтверждённого адреса, чтобы endpoint не раскрывал список аккаунтов.

Google проверяется сервером как подписанный ID token с точным audience.
Яндекс использует серверный authorization-code flow: secret не попадает в
браузер или APK. Callback выдаёт не сессию, а короткоживущий одноразовый код,
который клиент отдельно обменивает на сессию. Почта OAuth-аккаунта считается
подтверждённой только после проверки провайдером.

**Настольные приложения.** На Windows и Linux нативного SDK Google нет, поэтому
приложение открывает системный браузер и принимает ответ на `127.0.0.1` со
случайным свободным портом:

* Google — `/v1/auth/google/desktop`. Приложение приносит authorization code и
  PKCE-верификатор, сервер меняет их на ID token своим client secret. Обмен
  делает сервер, а не клиент: секрет не должен лежать в файле программы, а
  ID token приходит нам напрямую от Google.
* Яндекс — тот же `/v1/auth/yandex/start`, но с `returnTarget: "desktop"` и
  `returnUrl` вида `http://127.0.0.1:<порт>/…`. Адрес проверяется при начале
  входа (`api.parseLoopbackURL`) и хранится рядом со `state`. Без проверки
  эндпойнт стал бы открытым редиректором, уводящим одноразовый код наружу.

Оба сценария требуют клиента типа **Desktop app** в Google Cloud Console:
web-клиенту Google запрещает возврат на петлевой адрес.

Токен сессии — случайные 32 байта. В базе лежит только его SHA-256, поэтому
утечка дампа не даёт войти в чужой аккаунт. Пароли — argon2id, параметры
подобраны под одноядерную машину и записаны в саму строку хеша, так что их
можно ужесточить позже, не ломая существующие аккаунты.

Ответ на неверный пароль неотличим от ответа на несуществующий адрес: иначе
перебором можно было бы выяснить, кто зарегистрирован.

Одноразовые токены подтверждения, OAuth state и completion code также хранятся
только как SHA-256. Их таблицы и `users.email_verified_at` создаёт миграция
`0004_auth_providers.sql`.

### Синхронизация

```text
GET  /v1/sync/changes?since=<курсор>&limit=<n>
POST /v1/sync/push            {books, vocabulary, reviews}
POST /v1/sync/content/check   {shas: [...]}
PUT  /v1/sync/content/{sha}   [абзацы книги]
GET  /v1/sync/content/{sha}
POST /v1/sync/content/purge
```

Модель: у каждой записи есть глобальный `uuid` и время последнего изменения.
Пользователь имеет монотонный счётчик `sync_rev`; изменённая запись получает
очередное значение, клиент забирает всё, что новее его курсора. Конфликты
разрешаются по времени — побеждает более позднее изменение.

Счётчик увеличивается под advisory-локом пользователя. Это не украшение: без
него транзакция с меньшим номером могла бы зафиксироваться позже, чем клиент
прочитал больший, и запись навсегда проскочила бы мимо курсора. Инвариант
проверяется тестом `TestPullPagesCoverEveryRecordExactlyOnce`.

Тексты книг синхронизируются отдельно и адресуются содержимым: одна и та же
книга с двух устройств совпадает по sha256 и хранится один раз.

Адрес считают три реализации на разных языках, и он обязан совпадать байт в
байт. Поэтому хешируется **не JSON**, а абзацы с префиксом длины:
длина в байтах, перевод строки, сам абзац — и так подряд. Через JSON нельзя: Go всегда экранирует U+2028 и
U+2029 (ради безопасности встраивания в JavaScript), а `JSON.stringify` и
`jsonEncode` в Dart выводят их как есть. Символы эти приходят из текста Word, и
книга с ними просто не выгружалась бы: сервер посчитал бы другой адрес и отверг
запрос. Префикс длины обязателен — простого разделителя мало, любой символ
встретится внутри абзаца и склеит разные книги в одну.

Парные наборы примеров: `content_test.go`,
`frontend/test/services/sync_content_test.dart`, `web/src/lib/content.test.ts`.

### Прогресс курса

```text
GET /v1/course/progress/{courseId}
PUT /v1/course/progress/{courseId}   {updatedAt, payload}
```

`payload` хранит совместимую структуру прогресса Flutter и React: результаты
уроков, mastery, серию, XP и активный урок. Сервер применяет last-write-wins по
`updatedAt`, отвергает payload больше 512 КиБ и не позволяет времени далеко из
будущего навсегда победить нормальные обновления. Миграция
`0002_course_progress.sql` применяется автоматически при старте.

### Курсы и администрирование

```text
GET  /v1/course/bundle/{courseId}                 опубликованный bundle
GET  /v1/admin/overview                           продуктовые показатели
GET  /v1/admin/users?q=                           пользователи
GET  /v1/admin/incidents?status=open|all          инциденты
POST /v1/admin/incidents/{id}/resolve
GET  /v1/admin/courses
GET  /v1/admin/courses/{id}
POST /v1/admin/courses                            создать черновик
PUT  /v1/admin/courses/{id}                       сохранить черновик
POST /v1/admin/courses/{id}/publish               опубликовать
```

Роль хранится в `users.is_admin`, а `CITAVUK_ADMIN_EMAILS` только повышает
существующие аккаунты при старте. Курс редактируется как черновик. При
сохранении сервер пересчитывает `contentChecksum`; при публикации проверяет,
что в курсе есть разделы, уроки и упражнения. Предыдущая опубликованная версия
переходит в архив. HTTP-ответы `5xx` автоматически агрегируются в `incidents`.

### Перевод

```text
POST /v1/translate           {text, source, target}
POST /v1/translate/context   {sentence, start, end, source, target}
GET  /v1/translate/usage
GET  /translate?q=...        совместимость со старым клиентом
```

Ключевой факт, определивший устройство этой части: **DeepL отлично переводит
связный текст и разваливается на одиночных словах.** Замеры на живом API:

| вход | результат |
|---|---|
| `Ovo je velika kuća sa baštom.` | «Это большой дом с садом.» — верно |
| `kuća` | «собака» — неверно |
| `кућа` | «"Адвокат дьявола"» — неверно |

Это известное поведение нейронного перевода на входе без синтаксиса. Поэтому:

- связный текст идёт в DeepL;
- слово в читалке помечается тегом `<w>` и переводится **внутри предложения**
  через `tag_handling=xml` — тогда `kuća` даёт «дом», а не «собака», и один
  запрос возвращает сразу перевод фразы и выровненное слово;
- одиночное слово без контекста уходит запасному провайдеру, который на таком
  входе ведёт себя предсказуемо.

`start` и `end` — смещения в **байтах UTF-8**. Клиент на Dart индексирует
строку в единицах UTF-16, и для кириллицы эти числа не совпадают, поэтому он
пересчитывает их перед отправкой (`utf8ByteOffset`). Сервер дополнительно
проверяет, что границы не рассекают символ.

Переводы кешируются в общей на всех пользователей таблице: сербские слова
повторяются от текста к тексту, и общий кеш кратно снижает расход квоты.

## Развёртывание

```bash
cd server
./deploy/deploy.sh            # собрать и выкатить
./deploy/deploy.sh --nginx    # плюс обновить vhost
```

Сервер общий: там же работают ISPmanager, чужие сайты, почта и DNS. Скрипт
трогает только `/opt/citavuk`, свой unit и отдельный файл в `conf.d`.

Unit ограничивает сервис по памяти (256 МБ) и процессору (70%): на машине 1,8 ГБ
и одно ядро, и всплеск нагрузки на API не должен ронять соседние сервисы.

### Домен

`https://api.citavuk.ru` работает: A-запись ведёт на `85.137.89.21`, сертификат
Let's Encrypt выпущен, HTTP редиректит на HTTPS, продление автоматическое.

Приложение ходит только по HTTPS — по открытому каналу токен сессии передавать
нельзя, и это не настраивается.

## Подкасты и то, что осталось на Python

Проксируются на прежний сервис: `/analyze`, `/news`, `/article`, `/img`,
`/audio/proxy`, `/audio/tts`, `/documents/*`. Список путей явный, а не «всё
неизвестное наверх»: открытый прокси превратил бы сервер в средство обхода
ограничений чужой сети.

`/audio/lessons` и `/audio/transcript` уже обслуживает Go
(`internal/podcast`). Каталог строится из RSS, но сами реплики берутся только
из `https://citavuk.ru/transcripts/index.json`, где лежат проверенные
расшифровки Groq Whisper с пословными таймингами. RSS-описание никогда не
превращается в реплики. Эпизод без готового JSON возвращается с пустыми
`cues` и без `transcript_url`.

Порт на Go имеет смысл делать по одному разделу, и первым — новости: они не
требуют моделей и укладываются в стандартную библиотеку. Разбор CLASSLA
переносить сложнее всего, а на этой машине он ещё и не поместится по памяти.
