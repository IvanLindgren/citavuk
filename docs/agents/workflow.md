# Как вносить изменения

Порядок работы над задачей: от поиска поверхности до выкатки.
Таблица обязательных проверок — «Запустить проверки по затронутой зоне».

## Определить поверхность и контракт

1. Выполнить `git status --short` и сохранить чужие незавершённые изменения.
2. Найти точку входа через `rg`: маршрут/экран, вызываемый service/API, модель и
   место хранения. Не начинать с правки одного компонента без чтения соседних
   слоёв.
3. Решить, меняется ли только UI или также сетевой контракт, локальная схема,
   общий bundle, прогресс, синхронизация либо генератор ассетов.
4. Найти парные реализации. Особенно опасны: Dart/TypeScript reflow и content
   hash, SRS, разбиение сербских букв, course models, reader settings и UTF-8
   offsets.
5. До редактирования записать инварианты данных: офлайн-запуск, tombstones,
   `dirty` только после ack, lazy content, совместимость со старым клиентом.

## Реализовать минимальный вертикальный сценарий

- Модель и валидация должны появляться до UI, API и миграция — до клиента,
  который на них полагается. Для необязательной серверной функции оставлять
  локальный fallback.
- Пользовательский ввод валидировать на границе. URL проверять allowlist и DNS,
  файлы — по размеру и сигнатуре, JSON — по типам и лимитам. Ошибки сети не
  должны уничтожать локальные данные или снимать `dirty`.
- Новый экран переиспользует существующие `request`, `WordReader`, auth state,
  sync и дизайн-токены. Не создавать второй HTTP-клиент, вторую реализацию
  перевода или отдельный механизм сессий.
- Для временного события отдельно задаются стабильный id, временное окно,
  guest gate, локальная схема прогресса, merge с сервером и правило награды.
- Генерируемые файлы получать штатным скриптом. В коммит включать только те
  outputs, которые реально нужны runtime и намеренно отслеживаются Git.

## Покрыть риски тестами

- Чистую логику проверять unit-тестами рядом с модулем.
- Маршруты и сериализацию проверять contract-тестами на старом и новом payload.
- Миграции проверять на базе предыдущей версии, а не только на пустой БД.
- Авторизацию проверять как минимум в трёх состояниях: гость, обычный аккаунт,
  истёкшая/отозванная сессия; admin-функции ещё и обычным аккаунтом.
- Responsive UI проверять на desktop и узком viewport, включая длинный русский
  текст, меню, отсутствие горизонтального overflow и модальные слои.
- Внешний контент проверять по фактическому файлу/ответу и фиксировать источник
  и лицензию. Наличие URL само по себе не является проверкой.

## Запустить проверки по затронутой зоне

| Зона | Минимальные команды |
|---|---|
| React | `cd web; npm run lint; npm test; npm run build` |
| Go API | `cd server; gofmt -w <изменённые .go>; go test ./...; go vet ./...; go build ./...` |
| Python | `python -m py_compile backend/main.py backend/urlguard.py backend/ratelimit.py backend/analysis_cache.py` и релевантные `unittest` |
| Flutter | `cd frontend; flutter test; dart analyze lib; flutter build windows --debug` |
| Course content | `cd tools/course_build; go test ./...; go run . -out ../../frontend/assets/course/course_bundle.json` |
| Английский словарь | `python tools/build_english_lexicon.py` — нужны `nltk`, `regex` и корпуса `wordnet`/`brown`/`universal_tagset`. ⚠️ venv лежит внутри репозитория, и защитный хук nltk блокирует свои же импорты из текущего каталога: скрипт сам уходит во временный каталог, руками интерпретатор запускать только оттуда же |
| Сайт + приложение | проверки React и Flutter; при изменении API также полный набор Go |

После добавления или удаления Flutter-пакета перед проверками обязательно
`flutter clean` и `flutter pub get`. Предупреждение Vite о размере чанка не
равно ошибке, но новый крупный экран должен оставаться lazy. Пропущенную из-за
отсутствия БД, ключа или платформы проверку явно указывать в отчёте.

## Проверить diff и выпустить

1. Выполнить `git diff --check`, просмотреть `git diff --stat` и полный diff
   изменённых контрактов, миграций, конфигурации и generated manifests.
2. Не коммитить `.env`, OAuth secrets, SSH-ключи, signing key, модели CLASSLA,
   `node_modules`, `dist` и локальные базы/кеши.
3. Коммит должен содержать один завершённый сценарий вместе с тестами,
   миграциями, runtime-ассетами и актуализацией `AGENTS.md`/README.
4. Серверный контракт выкладывать до клиента. Статику сайта — до публикации
   приложений, если приложение скачивает каталог или assets с `citavuk.ru`.
5. Сайт: `cd web && ./deploy/deploy.sh`. Флаг `--nginx` использовать только
   при осознанном изменении vhost. Go: `cd server && ./deploy/deploy.sh`.
   Приложения публикуются отдельно через `web/deploy/publish-apps.sh`. Перед
   production-деплоем дождаться зелёного `.github/workflows/ci.yml` именно для
   выкладываемого коммита; workflow проверяет web и server, но сам не деплоит.
6. После деплоя проверить публичные URL, Content-Type, lazy route, гостевой и
   авторизованный сценарии, консоль браузера и один узкий viewport.
7. Только после успешных проверок отправлять коммит в GitHub. Не делать
   force-push общей ветки и не переписывать чужую историю.
