# Master-prompt: полная переработка грамматики Citavuk в игровой учебный курс

Ниже находится готовый большой промпт для coding-агента. Передай агенту весь
текст между разделителями `НАЧАЛО ПРОМПТА` и `КОНЕЦ ПРОМПТА` без сокращений.

---

# НАЧАЛО ПРОМПТА

Ты работаешь над существующим проектом **Citavuk / «Читавук»** — Flutter-
приложением для русскоязычных людей, изучающих сербский язык через чтение,
перевод, грамматический разбор, карточки, новости и аудирование.

Твоя задача — **полностью переработать пользовательский раздел «Грамматика»**:
вместо статического списка правил он должен стать небольшим, но законченным
игровым курсом с последовательной траекторией уроков, интерактивными
упражнениями, прогрессом, контрольной работой и маскотом Читавуком.

Курс должен использовать понятные и проверенные механики современных
language-learning apps: короткие уроки, одно действие на экран, немедленная
обратная связь, чередование типов заданий, повторение ошибок и наглядный путь
прогресса. При этом **не копируй дословно интерфейс, тексты, звуки, графику,
бренд, персонажей или закрытые алгоритмы Duolingo**. Создай самостоятельный
продукт в визуальном языке Citavuk. Сходство должно быть на уровне
педагогической механики, а не пиксельной копии.

Работай непосредственно с репозиторием. Не ограничивайся планом или макетом:
после изучения проекта реализуй функцию end-to-end, включая модели, хранение,
бэкенд, UI, упражнения, авторизацию, тесты, миграции и документацию.

## 0. Обязательная целевая архитектура

На момент начала задачи в Citavuk:

- регистрации и серверной базы пользователей ещё нет;
- существующий бэкенд написан на Python/FastAPI;
- пользовательские книги и словарь хранятся локально на устройстве;
- учебный прогресс нового курса ещё не имеет серверного хранилища.

В рамках этой переработки необходимо:

1. Создать регистрацию, авторизацию и синхронизацию прогресса.
2. Использовать **PostgreSQL** как единственное production-хранилище
   пользователей, сессий, прогресса курса, попыток, mastery и контрольных.
3. **Полностью переписать production-бэкенд Citavuk с Python на Go.**
4. После миграции production-контейнер не должен требовать Python, FastAPI,
   Uvicorn, CLASSLA Python package, `deep-translator`, `trafilatura` или `gTTS`.
5. Сохранить либо осознанно заменить все существующие возможности бэкенда:
   разбор слов, перевод, новости, статьи, прокси изображений, радио/аудио,
   транскрипции, TTS, курируемые аудиоуроки и health endpoint.
6. Не удалять старый Python-бэкенд до появления parity tests и подтверждения,
   что Go-реализация покрывает необходимые клиентские контракты. После
   подтверждения удалить production Python path, зависимости и старый Docker
   entrypoint, оставив историю в Git.
7. Не переносить локальные книги пользователя в PostgreSQL. `UserDb` остаётся
   локальным хранилищем чтения; PostgreSQL обслуживает аккаунт и учебный курс.

Нельзя закончить задачу состоянием «Flutter использует новый Go API только для
аккаунтов, а старый Python остаётся для остальных endpoints». Целевой
production backend должен быть единым Go-приложением.

## 2. Неприкосновенная функциональность

Новый курс заменяет только пользовательский раздел «Грамматика» на главной.
Он **не должен ломать или удалять**:

- импорт и чтение PDF/DOCX;
- перевод слова и фразы;
- контекстный перевод;
- словарь книги;
- карточки SRS;
- новости;
- радио;
- аудирование;
- `GrammarScreen`, открываемый из разбора конкретного слова;
- `GrammarEngine.describe()`;
- `GrammarEngine.buildParadigms()`;
- управление предлогов;
- разбор составных времён и энклитик;
- офлайн-морфологию native-платформ.

`GrammarEngine` остаётся инфраструктурой грамматического анализа в читалке.
Разрешается вынести из него учебные темы и старые flip-карточки, если они
переносятся в новый content layer, но нельзя удалить функции, используемые
`BookReaderScreen`, `GrammarScreen`, `VocabularyScreen` или
`AnalysisRepository`.

Чтение и перевод остаются доступны **без регистрации**. Нельзя ставить
глобальный auth wall при запуске приложения.

## 3. Главный результат

После реализации пользователь должен видеть:

1. На главной прежнюю точку входа «Грамматика», ведущую в новый курс.
2. Если пользователь не авторизован:
   - аккуратный экран-превью курса;
   - объяснение, что аккаунт нужен только для сохранения учебного прогресса;
   - кнопки «Создать аккаунт» и «Войти»;
   - явную кнопку «Вернуться к чтению»;
   - отсутствие блокировки остальных функций Citavuk.
3. После регистрации:
   - карту курса с разделами и уроками;
   - текущий урок;
   - завершённые и заблокированные узлы;
   - общий процент;
   - серию учебных дней;
   - накопленный опыт или аналогичный показатель;
   - отдельный блок повторения ошибок;
   - отдельный раздел «Тренажёрка» для неограниченной практики выбранных тем;
   - итоговую контрольную после прохождения курса.
4. При открытии урока:
   - короткое вступление;
   - серия интерактивных упражнений;
   - Читавук со sprite-анимациями;
   - прогресс урока;
   - проверка каждого ответа;
   - понятное объяснение ошибки;
   - итог урока;
   - сохранённый серверный прогресс.
5. После курса:
   - итоговая контрольная;
   - результат по темам;
   - список слабых тем;
   - возможность повторить ошибки;
   - статус освоения курса.
6. В «Тренажёрке»:
   - выбор одной или нескольких уже доступных грамматических тем;
   - режим «Слабые места»;
   - режим смешанной практики;
   - бесконечная подача новых упражнений без искусственного финала;
   - ручное завершение сессии;
   - итог текущей тренировки и обновление mastery.

## 4. Источник курса: книга Просвирниной

Курс должен строиться **полностью на основе предоставленного Markdown-файла
книги Просвирниной по сербской грамматике**.

### 4.1 Запрет на выдуманный контент

Не генерируй грамматические утверждения «по памяти», если они могут быть
извлечены из книги. Не используй существующий `GrammarEngine.grammarTopics()`
как главный источник истины: в нём могут быть упрощения и ранее обнаруженные
ошибки.

Для каждого учебного правила:

- найди соответствующий раздел книги;
- сохрани внутреннюю ссылку на источник: заголовок, anchor или диапазон
  смыслового раздела;
- преобразуй правило в короткое авторское объяснение;
- создай примеры на основе правила;
- проверь примеры морфологическим движком, где это возможно;
- не копируй большие фрагменты книги дословно;
- не меняй смысл правила ради игровой механики.

Если книга не содержит нужного утверждения, не добавляй его в обязательную
траекторию без отдельной пометки `supplemental` и проверяемого источника.

### 4.2 Content provenance

Каждая тема курса должна иметь метаданные:

```text
sourceBook
sourceHeading
sourceAnchor
sourceEditionOrFileHash
contentVersion
reviewStatus
reviewedBy
```

`reviewStatus`:

- `draft`;
- `machine_checked`;
- `teacher_reviewed`.

В production UI не обязательно показывать технические поля, но данные должны
сохраняться, чтобы преподаватель мог проверить происхождение упражнения.

### 4.3 Компиляция контента

Не парси всю книгу во время каждого запуска Flutter-приложения. Создай
детерминированный build/import pipeline:

1. Markdown книги читается инструментом генерации.
2. Заголовки и секции превращаются в нормализованный course source.
3. Ручная course specification связывает темы с упражнениями.
4. Валидатор проверяет ID, ссылки, ответы и prerequisites.
5. Клиент получает компактный versioned JSON или данные через API.

Предпочтительно хранить исходный учебный контент в репозитории как
редактируемые JSON/YAML/Markdown-файлы, а не в огромной Dart-константе.

Content build должен быть воспроизводимым. Случайная генерация примеров во
время build допустима только с фиксированным seed и обязательной валидацией.

## 5. Педагогическая структура курса

Сначала извлеки оглавление и последовательность тем из книги. Не навязывай
книге заранее выдуманный порядок. Затем преврати содержание в игровую
траекторию.

Рекомендуемая иерархия:

```text
Course
  Unit / Раздел
    Skill / Тема
      Lesson / Урок
        Intro
        Exercise[]
        LessonResult
    UnitCheckpoint
  FinalExam
```

### 5.1 Размеры

- Один урок: ориентировочно 6–12 упражнений.
- Целевая длительность: 4–8 минут.
- Одна новая микроконцепция на урок.
- После 2–4 новых упражнений — закрепление.
- В конце урока — минимум одно задание на активное воспроизведение.
- После нескольких уроков темы — смешанное повторение.
- После раздела — checkpoint.
- В конце всего курса — комплексная контрольная.

Это ориентиры, а не жёсткие числа. Не раздувай урок только ради количества.

### 5.2 Порядок сложности

Внутри темы:

1. Узнавание формы.
2. Выбор формы с подсказкой.
3. Сборка формы.
4. Сборка предложения.
5. Самостоятельное применение в новом контексте.
6. Смешение с ранее изученными правилами.

Не проверяй новую конструкцию до того, как она была кратко объяснена или
продемонстрирована.

### 5.3 Повторение

Добавь:

- повтор ошибок в конце урока;
- очередь слабых упражнений;
- interleaving старых тем;
- повтор тем с низким mastery;
- возможность вручную повторить завершённый урок;
- ежедневную короткую практику.

Прогресс должен измерять не только факт открытия урока, но и успешность по
конкретным learning objectives.

## 6. Типы упражнений

Сделай расширяемую архитектуру. Не кодируй весь урок одним большим `switch` в
экране. Каждое упражнение должно иметь:

- типизированную модель;
- отдельный renderer/widget;
- отдельный evaluator;
- сериализацию;
- accessibility semantics;
- unit tests;
- стабильный `exerciseId`;
- ссылку на `skillId`, `lessonId` и `learningObjectiveId`.

Обязательны следующие типы.

### 6.1 Составление предложения из слов

Пользователь видит:

- инструкцию на русском или сербском;
- при необходимости русский смысл;
- банк слов;
- область собранного предложения;
- кнопку проверки.

Поведение:

- tap перемещает слово из банка в ответ;
- tap по слову в ответе возвращает его;
- drag-and-drop доступен как дополнительный способ, но tap должен работать на
  мобильном и для accessibility;
- одинаковые слова имеют разные token IDs;
- порядок можно сбросить;
- длинные предложения переносятся без overflow;
- банк слов не меняет высоту хаотично;
- после ответа показывается правильный порядок и объяснение.

Поддержать:

- один правильный порядок;
- несколько допустимых порядков слов;
- optional tokens;
- клитики и фиксированные позиции;
- пунктуацию;
- сербскую латиницу и кириллицу, если урок это допускает.

Evaluator не должен принимать любой порядок только потому, что набор слов
совпадает.

Пример модели:

```json
{
  "type": "sentence_builder",
  "id": "perfekat_l2_e4",
  "prompt": "Составьте: «Вчера я видел Марко»",
  "tokens": [
    {"id": "t1", "text": "Juče"},
    {"id": "t2", "text": "sam"},
    {"id": "t3", "text": "video"},
    {"id": "t4", "text": "Marka"},
    {"id": "t5", "text": "."}
  ],
  "acceptedOrders": [
    ["t1", "t2", "t3", "t4", "t5"]
  ],
  "explanation": "...",
  "sourceRef": "..."
}
```

### 6.2 Подбор правильного окончания глагола

Показывай слово с визуально отделённой основой и слотом окончания:

```text
rad + [im / iš / i / imo]
```

Варианты могут быть:

- chips;
- список;
- компактная таблица лиц;
- drag окончания в слот.

Проверять:

- лицо;
- число;
- время;
- наклонение;
- согласование причастия по роду/числу;
- вид там, где он релевантен.

После ошибки объяснять не только «неверно», а:

```text
Подлежащее «mi» — 1-е лицо множественного числа.
В презенте здесь нужна форма «radimo».
```

Не вычислять все ответы наивным удалением последних двух букв инфинитива.
Использовать проверенные формы course content и лексикон. Если применяется
генератор `GrammarEngine`, generated forms должны пройти content validation.

### 6.3 Подбор окончания существительного

Показывать:

- предложение;
- выделенное существительное;
- контекст или предлог;
- основу;
- варианты окончания;
- при необходимости вопрос падежа.

Проверять:

- падеж;
- число;
- род;
- одушевлённость;
- управление предлога;
- чередование основы.

Объяснение ошибки должно связывать форму с синтаксическим контекстом:

```text
После «bez» нужен родительный падеж.
У существительного «knjiga» Gen. Sg. — «knjige».
```

Не сводить упражнение к механическому suffix matching там, где меняется
основа.

### 6.4 Описание изображения

Это отдельное семейство заданий. Изображение должно быть реальным учебным
содержанием, а не декоративным фоном.

Минимум три режима:

1. Выбрать предложение, правильно описывающее изображение.
2. Собрать описание из слов.
3. Заполнить правильную форму в готовом описании.

Дополнительный advanced-режим:

4. Ввести короткое описание самостоятельно.

Для free-text:

- не сравнивать только с одной строкой;
- иметь ограниченный список accepted answers;
- нормализовать регистр, пробелы и терминальную пунктуацию;
- не принимать грамматически неправильный ответ только по semantic similarity;
- при отсутствии надёжного evaluator использовать выбор/сборку, а не LLM-судью.

Каждое изображение должно иметь:

- asset ID;
- локальный путь или доверенный CDN URL;
- лицензию/происхождение;
- alt text;
- список изображённых сущностей;
- целевые конструкции;
- accepted descriptions;
- crop/focal point для responsive layout.

Не загружать случайные изображения из поисковика в production. Использовать
созданные пользователем, лицензированные или специально сгенерированные
ассеты с зафиксированной provenance.

### 6.5 Сборка перемешанного слова из букв

Показывается набор букв правильной словоформы в перемешанном порядке.
Пользователь должен переставлять буквы и собрать форму.

Обязательное поведение:

- каждая буква — отдельная плитка с уникальным ID;
- повторяющиеся буквы не конфликтуют;
- drag-and-drop работает мышью и touch;
- tap-select + tap-target является доступной альтернативой;
- есть кнопка сброса;
- допускается keyboard reordering на desktop/web;
- диакритики `č`, `ć`, `š`, `ž`, `đ` являются едиными буквами;
- диграфы `lj`, `nj`, `dž` по умолчанию остаются двумя Unicode-символами,
  если конкретный урок явно не учит их как буквенную единицу;
- shuffle не должен случайно оставить правильное слово в исходном порядке;
- shuffle детерминирован для текущей попытки;
- после ошибки показывается разбор основы и окончания.

Пример:

```text
Контекст: «Разговариваем с другом.»
Лемма: prijatelj
Нужно: instrumental singular
Плитки: e, m, p, r, i, j, a, t, e, l, j
Ответ: prijateljem
```

Сложность регулируется:

- наличием контекста;
- показом леммы;
- подсветкой основы;
- количеством лишних букв;
- длиной слова.

### 6.6 Дополнительные полезные типы

После обязательных типов можно добавить:

- multiple choice значения формы;
- matching «предлог → падеж»;
- matching «местоимение → форма глагола»;
- заполнение пропуска;
- исправление ошибки в предложении;
- выбор между похожими формами;
- мини-таблицу спряжения;
- перевод в контролируемом контексте.

Не добавляй тип ради количества. Он должен проверять конкретную цель.

Создай sealed hierarchy или другой типобезопасный механизм. Не передавай

Базовые поля:

```text

unitId
skillId
lessonId
learningObjectiveIds
difficulty
prompt
instructionLanguage
serbianScript
explanation
```

Типизированный parser должен:

## 8. Проверка ответов

Создай отдельный слой `AnswerEvaluator`.

### 8.1 Нормализация

Допустимо нормализовать:

- начальные/конечные пробелы;
- повторные пробелы;
- регистр, если цель не проверяет заглавную букву;
- terminal punctuation, если она не является целью;
- Unicode normalization;
- согласованные варианты кавычек.

Нельзя безусловно нормализовать:

- `č` и `ć`;
- `dž` и `đ`;
- падежные окончания;
- клитики;
- отрицание;
- порядок слов, если он проверяется;
- латиницу и кириллицу, если урок проверяет конкретную письменность.

### 8.2 Варианты ответа

Поддержать:

- exact accepted answers;
- accepted token orders;
- accepted inflection sets;
- optional punctuation;
- controlled alternate word order;
- script-equivalent answer только при `acceptBothScripts: true`.

Не использовать online translator как judge.

LLM или semantic similarity нельзя делать единственным судьёй грамматической
правильности. Для beta free-text можно использовать серверную проверку только
как дополнительную подсказку с явным fallback.

### 8.3 Обратная связь

Для правильного ответа:

- краткое подтверждение;
- при первом знакомстве — короткое reinforcement rule;
- позитивная анимация Читавука;
- переход дальше только после осознанного действия или короткой задержки.

Для ошибки:

- показать ответ пользователя;
- показать правильную форму;
- выделить различающуюся часть;
- объяснить правило;
- предложить «Понятнее»/«Показать правило»;
- добавить exercise/objective в очередь повторения;
- показать спокойную, не унижающую анимацию.

Не использовать только цвет. Добавить иконку и текст.

## 9. Карта курса

Создай самостоятельный экран course path.

### 9.1 Состояния узла

- `locked`;
- `available`;
- `inProgress`;
- `completed`;
- `mastered`;
- `needsReview`.

Узел должен иметь стабильный размер, чтобы badge, progress ring и анимация не
двигали layout.

### 9.2 Unlock logic

- первый урок доступен после регистрации;
- следующий открывается после минимального результата предыдущего;
- checkpoint открывается после обязательных уроков раздела;
- финальная контрольная открывается после всех обязательных разделов;
- повтор завершённых уроков доступен всегда;
- content update не должен без объяснения стирать старый прогресс.

### 9.3 Не копировать визуально Duolingo

Сделай путь в эстетике Citavuk:

- сербская красно-золотая палитра как акцент, но не однотонная;
- светлая и тёмная тема;
- орнамент используется умеренно;
- Читавук является первым визуальным сигналом курса;
- никаких чужих зелёных персонажей, корон, формулировок и звуков;
- карточки не вкладывать в карточки;
- mobile-first, но без пустого пространства на desktop.

Курс должен выглядеть как часть Citavuk, а не встроенный чужой сайт.

`sourceAnchor`.

## 11. Маскот Читавук: PNG-кадры, удаление фона и sprite atlas

В уроках используется Читавук, но уже не как одна статичная PNG-картинка.
Исходные анимации сейчас представляют собой **наборы отдельных PNG-кадров с
непрозрачным фоном**, а не готовые прозрачные sprite sheets.

Агент обязан самостоятельно:

1. Определить последовательности кадров.
2. Удалить непрозрачный фон, то есть сделать фон действительно прозрачным.
3. Визуально проверить результат.
4. Обрезать/выровнять кадры без дрожания персонажа.
5. Собрать оптимизированные sprite sheets/atlases.
6. Сгенерировать manifest.
7. Подключить полученные производные ассеты во Flutter.

Исходные PNG не удалять и не перезаписывать. Хранить отдельно:

```text
animations/source/                 # оригинальные кадры пользователя
frontend/assets/animations/        # сгенерированные прозрачные atlas/sheets
frontend/assets/animations/manifest.json
```

Если фактическая папка имеет другую структуру, адаптируй пути и задокументируй
их, но сохраняй разделение source/generated.

### 11.1 Инспекция последовательностей

Для каждой группы PNG определить:

- соглашение об именах и числовой порядок;
- отсутствующие/дублирующиеся кадры;
- ширину и высоту;
- одинаков ли canvas;
- цвет или тип непрозрачного фона;
- касается ли персонаж границ;
- тени, светлые волосы/шерсть и детали, похожие на фон;
- положение ног/центра массы;
- желаемый FPS;
- loop или one-shot;
- semantic state.

Не полагайся на лексикографическую сортировку (`frame_10` не должен идти перед
`frame_2`). Используй natural numeric ordering.

### 11.2 Воспроизводимое удаление фона

Создай build-time инструмент в репозитории. Он может быть написан на Go или
Dart; он не является production-бэкендом. Не делай обработку изображений на
устройстве пользователя.

Алгоритм должен:

- использовать углы/границы кадра для оценки фона;
- удалять только связанный с границами фон через flood fill/segmentation;
- применять контролируемый color-distance threshold;
- не удалять похожий цвет внутри замкнутых деталей персонажа;
- сохранять белки глаз, зубы, блики и светлые участки;
- формировать корректный alpha channel;
- слегка очищать color spill по краю;
- делать умеренное feathering, не создавая белого/цветного ореола;
- одинаково обрабатывать всю последовательность;
- выдавать diagnostic mask и preview montage;
- завершаться ошибкой при подозрительно большой потере foreground pixels.

Нельзя просто сделать глобальный `replaceAll(backgroundColor → transparent)`:
это может вырезать части Читавука.

Если фон сложный, неоднородный или касается персонажа, используй
foreground matting/segmentation с последующей ручной визуальной проверкой.
Автоматическая обработка без QA не считается выполненной.

### 11.3 Стабилизация кадров

После удаления фона:

- найди alpha bounding box;
- вычисли общий canvas для всей анимации;
- выровняй кадры по устойчивому anchor, обычно низ/центр персонажа;
- не центрируй каждый кадр независимо, создавая прыжки;
- сохрани движение, которое было частью исходной анимации;
- добавь безопасный padding;
- проверь montage и короткий preview;
- не меняй aspect ratio персонажа.

### 11.4 Сборка atlas и manifest

Собирай прозрачные производные кадры в atlas/sprite sheet с ограничением
максимального размера текстуры. Если одна анимация слишком велика, разбей её на
несколько sheets и отрази это в manifest.

Пример manifest:

```json
{
  "id": "citavuk_happy",
  "asset": "assets/animations/generated/citavuk_happy.png",
  "frameWidth": 512,
  "frameHeight": 512,
  "columns": 8,
  "rows": 1,
  "frames": 8,
  "fps": 12,
  "loop": false,
  "anchor": {"x": 0.5, "y": 1.0}
}
```

Manifest генерируется детерминированно и содержит checksum исходной
последовательности, чтобы понимать, когда atlas устарел.

### 11.5 Нужные состояния

Свяжи доступные вариации с состояниями:

- `idle`;
- `thinking`;
- `encourage`;
- `correct`;
- `incorrect`;
- `hint`;
- `lessonComplete`;
- `checkpoint`;
- `finalCelebration`.

Если вариаций меньше, переиспользуй наиболее близкие. Не генерируй новые без
запроса пользователя.

### 11.6 Sprite renderer

Создай переиспользуемый `SpriteAnimation`/controller:

- один decode изображения;
- кадры через source rectangle;
- отсутствие отдельного asset decode на каждый frame;
- precache до начала урока;
- pause при background;
- dispose ticker/controller;
- respect `MediaQuery.disableAnimations`;
- статичный fallback при reduced motion;
- configurable fit и anchor;
- frame switching без изменения размеров layout;
- error fallback на существующий `Wolf.*` asset;
- тест manifest parser.

Не создавай сотни `Image.asset` в секунду.

### 11.7 Визуальная проверка

Для каждой анимации сгенерируй:

- contact sheet до обработки;
- contact sheet после;
- preview на светлом фоне;
- preview на тёмном фоне;
- preview на красном/контрастном фоне;
- alpha matte.

Проверь отсутствие:

- старого прямоугольного фона;
- ореола;
- дыр в персонаже;
- обрезанных ушей, лап и хвоста;
- дрожания;
- скачущего размера;
- пустых кадров.

### 11.8 Поведение

- Idle анимация не должна отвлекать постоянно.
- Correct/incorrect запускаются после evaluation.
- One-shot возвращается в idle.
- Lesson complete не проигрывается повторно при rebuild.
- Mascot не закрывает вопрос, варианты и CTA.
- Звук не включать автоматически без отдельной настройки.

## 12. Аккаунты и авторизация

Регистрация обязательна только для входа в игровой курс и синхронизации
прогресса.

### 12.1 Guest mode

Без аккаунта работают:

- библиотека;
- импорт документов;
- чтение;
- перевод;
- разбор грамматики слова;
- словарь;
- карточки;
- новости;
- радио;
- аудирование, если оно не требует отдельной серверной учётной записи.

Нельзя:

- показывать login dialog при каждом запуске;
- блокировать Dashboard;
- скрывать пользовательские книги;
- удалять локальные данные при logout.

### 12.2 Auth flow

Минимум:

- регистрация email + пароль;
- вход;
- подтверждение email, если инфраструктура это поддерживает;
- восстановление пароля;
- logout;
- просмотр состояния аккаунта;
- удаление аккаунта;
- понятные ошибки;
- loading и retry;
- rate limiting на сервере.

Пароль:

- никогда не хранится в Flutter;
- никогда не логируется;
- на сервере хранится только современный password hash;
- минимальная длина и разумная проверка;
- не ограничивать допустимые символы без необходимости.

Токены:

- короткоживущий access token;
- безопасный refresh flow;
- native secure storage;
- web-стратегия с учётом XSS/CSRF;
- автоматическое обновление;
- logout invalidation;
- не помещать секретный server key в клиент.

Не хранить production accounts в SQLite-файле Hugging Face Space: его диск
может быть эфемерным. Используй постоянное внешнее хранилище, рассчитанное на
аккаунты. Предпочтительная архитектура:

- единый Go API обслуживает auth, курс и все прежние endpoints Citavuk;
- production DB — внешний PostgreSQL через `DATABASE_URL`;
- Go database layer использует `pgx`/`pgxpool` или обоснованный эквивалент;
- локальная разработка использует PostgreSQL в Docker, а не отдельную
  SQLite-схему с другим поведением;
- schema migrations версионируются и выполняются отдельной Go migration
  командой/проверенной библиотекой;
- приложение проверяет доступность и версию схемы при старте, но не выполняет
  опасные необратимые миграции молча;
- секреты задаются environment variables;
- repository/service layer отделяет auth/progress от HTTP handlers;
- connection pool имеет limits, timeouts и graceful shutdown;
- транзакции используются для связанных обновлений progress/mastery/streak.

Регистрации и базы пользователей в исходном проекте нет: не делай вид, что
интегрируешь готовую схему. Создай её с нуля в PostgreSQL, добавь migrations,
indexes, uniqueness constraints и integration tests.

### 12.3 Privacy

Собирай минимум:

- user ID;
- email;
- password hash или provider ID;
- timestamps;
- course progress;
- attempts/mastery;
- streak metadata.

Не отправляй тексты пользовательских книг в профиль курса без отдельного
согласия.

Добавь:

- privacy notice;
- удаление данных;
- экспорт прогресса в машиночитаемом формате;
- версию terms/privacy acceptance, если это требуется выбранной схемой.

## 13. Прогресс и синхронизация

### 13.1 Серверные сущности

Спроектируй минимум:

```text

course_enrollments
lesson_progress
exercise_attempts
objective_mastery
review_queue
streaks

```

Примерные поля:


Не сохраняй пароль, access token или полный чувствительный payload попытки в

### 13.2 Local cache

Курс должен переживать временное отсутствие сети после успешного входа:

- кеш course content;
- кеш профиля;
- локальная очередь попыток;
- optimistic progress только там, где безопасно;
- sync status;
- retry с backoff;
- idempotency key для попыток;
- merge rule по server timestamps/content version.

Если полная offline-auth слишком велика для первой версии, приложение должно
как минимум честно показывать, что вход и первая загрузка требуют сети, а уже
открытый урок не должен терять ответы при кратком обрыве.

### 13.3 Streak

Серия дней:

- считается по локальной учебной дате пользователя;
- сервер хранит UTC timestamps и timezone context;
- повторная отправка одной попытки не удваивает день;
- изменение часов не должно легко ломать серию;
- streak не является основанием блокировать обучение.

## 14. API курса

Сделай стабильные versioned endpoints, например `/v1/...`.

Минимальный набор:

```text

POST   /v1/auth/login
POST   /v1/auth/refresh
POST   /v1/auth/logout
POST   /v1/auth/forgot-password
POST   /v1/auth/reset-password
DELETE /v1/account

GET    /v1/course
GET    /v1/course/progress
GET    /v1/course/lessons/{lesson_id}
POST   /v1/course/attempts
POST   /v1/course/lessons/{lesson_id}/complete
GET    /v1/course/review
POST   /v1/course/gym/sessions
POST   /v1/course/gym/sessions/{session_id}/next
POST   /v1/course/gym/sessions/{session_id}/finish
POST   /v1/course/exams/{exam_id}/submit
```

Требования:

- типизированные Go request/response structs;
- единый error envelope;
- validation;
- auth middleware;
- request size limits;
- idempotency;
- UTC timestamps;
- content version в ответах;
- no wildcard write endpoints;
- OpenAPI генерируется/проверяется для Go handlers и остаётся валидным;

Не отдавай клиенту правильные ответы там, где это позволяет тривиально пройти
итоговый экзамен через DevTools. Для обычных bundled lessons accepted answers
могут физически находиться в клиенте, но контрольная должна оцениваться на
сервере либо иметь отдельный защищённый вариант. Не изображай это как
абсолютную anti-cheat защиту: клиентское приложение полностью скрыть нельзя.

Предпочтительная структура:

```text

├── internal/news/
├── internal/audio/
├── internal/storage/postgres/
├── internal/storage/lexicon/
├── migrations/
├── go.mod
├── go.sum
└── tests/
```

Конкретный router можно выбрать после аудита, но не добавляй тяжёлый framework
без необходимости. Допустимы стандартный `net/http` или небольшой
поддерживаемый router. Для PostgreSQL предпочтителен `pgxpool`.

Перепиши корневой `Dockerfile` как multi-stage build:

- builder компилирует статически/предсказуемо Go binary;
- runtime содержит только binary, CA certificates и необходимые data assets;
- запуск от непривилегированного пользователя;
- порт Hugging Face Space остаётся 7860;
- healthcheck/readiness;
- никакого Python interpreter и pip cache;
- версия Go закреплена;
- binary корректно получает SIGTERM и завершает HTTP server/DB pool.

### 14.2 Совместимость Flutter-клиента

Существующие клиентские сервисы не должны одновременно ломаться. Для legacy
routes сохрани JSON contracts либо мигрируй Flutter и Go в одной согласованной
правке.

Перед переключением production URL:

1. Запусти старый Python и новый Go backend на разных портах.
2. Подготовь contract fixtures.
3. Сравни status codes, поля JSON, пустые состояния, content types, Range и
   CORS.
4. Выполни smoke tests Flutter против Go.
5. Только затем удали Python production path.

Не требуется сохранять старые внутренние ошибки и небезопасное поведение.

### 14.3 Замена Python-зависимых функций

Go production container не должен запускать Python subprocess.

- RSS: Go feed parser или надёжный XML parser.
- Извлечение статьи: Go readability/content extraction с fallback metadata.
- HTML transcript: Go HTML tokenizer/parser, не regex-only для всей разметки.
- Image/audio proxy: `net/http`, allowlist, SSRF protection, Range streaming.
- Перевод: provider interface поверх официального HTTP API; ключи только в
  environment. Сохрани fallback/cache strategy.
- TTS: provider interface поверх доступного HTTP TTS API либо другой
  обоснованный Go-compatible путь. Не вызывать `gTTS` через Python.
- SQLite lexicon: Go SQLite driver, выбранный с учётом Docker/CGO, или
  предварительный импорт лексикона в PostgreSQL.

### 14.4 NLP после отказа от CLASSLA Python

Нельзя молча удалить контекстный NLP и заменить его всегда на `UNKNOWN`.
Выбери и задокументируй Go-compatible стратегию:

- модель, экспортированная в формат, доступный Go runtime;
- внешний NLP provider через типизированный adapter;
- улучшенный PostgreSQL/SQLite lexicon path как гарантированный fallback;
- комбинация этих вариантов.

Требования:

- контракт `/analyze` сохраняет lemma/upos/feats/forms/translation/context;
- character offsets обрабатываются корректно;
- повтор одинакового слова в предложении не выбирается только по первому
  совпадению текста;
- fallback честно маркируется;
- corpus fixtures сравнивают Python baseline и Go result;
- допустимые расхождения документируются;
- деградация точности требует явного решения, а не скрытого merge.

### 14.5 PostgreSQL и миграции

Обязательно:

- schema migrations в Git;
- UUID или другой обоснованный тип ID;
- `citext` либо надёжная нормализация email + unique index;
- foreign keys;
- indexes для due review, progress и sessions;
- transactions;
- connection pool limits;
- statement/query timeouts;
- health/readiness различают процесс и БД;
- graceful shutdown;
- backup/restore инструкция;
- тест миграции с пустой базы и предыдущей версии.

Локальная разработка должна подниматься документированной командой через
Docker Compose или эквивалент:

```text
Go API + PostgreSQL
```

Не использовать SQLite как скрытую production-замену PostgreSQL.

## 15. Content delivery

Выбери и реализуй один ясный вариант:

### Вариант A: bundled core course

- базовый course JSON входит в Flutter assets;
- server сообщает актуальную версию;
- progress хранится server-side;
- обновления приложения обновляют content.

### Вариант B: versioned server course

- Flutter кеширует course manifest;
- server отдаёт versioned JSON;
- есть checksum;
- старый урок не меняется посреди активной попытки;
- assets имеют стабильные URL или входят в app.

Для beta предпочтителен bundled core course плюс server progress, если
изображения и контент не требуют частых независимых обновлений. Но решение
должно учитывать размер книги и изображений.

Нельзя отдавать в мобильный bundle исходный полный Markdown книги, если права
или размер этого не позволяют. В bundle должен попадать переработанный учебный
контент, а не обязательно весь источник.

## 16. Итоговая контрольная

После прохождения обязательных units открывается финальная контрольная.

### 16.1 Содержание

Она должна:

- проверять все ключевые learning objectives;
- использовать новые примеры, а не точные копии уроков;
- смешивать типы упражнений;
- включать активное воспроизведение;
- включать окончания глаголов;
- включать падежные окончания;
- включать сборку предложений;
- включать минимум одно задание по изображению;
- включать минимум одно перемешанное слово;
- проверять материал пропорционально важности темы.

### 16.2 Формирование

- версия экзамена фиксируется при старте;
- вопросы выбираются из проверенного пула;
- shuffle имеет server attempt seed;
- обязательное покрытие тем;
- отсутствие двух идентичных вариантов рядом;
- незавершённый экзамен можно безопасно восстановить;
- ответы не теряются при transient network failure.

### 16.3 Результат

Показывать:

- общий балл;
- passed/not passed;
- breakdown по разделам;
- сильные темы;
- темы для повторения;
- ошибки с объяснением после завершения;
- кнопку «Повторить слабые темы»;
- следующую допустимую попытку, если вводится cooldown.

Не использовать только один процент. Ученик должен понимать, что именно
повторять.

Pass threshold должен быть явной course config, а не magic number в UI.

## Отдельный раздел «Тренажёрка»

После регистрации рядом с картой курса должен быть самостоятельный раздел
**«Тренажёрка»**. Это не конечный урок и не контрольная: пользователь может
неограниченно практиковать выбранные грамматические темы.

### Режимы

Минимум:

1. **Выбрать темы** — одна или несколько уже открытых тем.
2. **Слабые места** — objectives с низким mastery или частыми ошибками.
3. **Смешанная практика** — материал из всех открытых разделов.
4. **Повтор ошибок** — недавние misconception IDs.
5. **Быстрая тренировка** — короткая сессия из заданного количества вопросов.
6. **Бесконечный режим** — вопросы подаются до ручного завершения.

Доступ к закрытым темам курса не должен позволять случайно пройти материал без
объяснения. Можно дать отдельную настройку «Все темы» только после завершения
соответствующего раздела или курса.

### Бесконечность без бесконечного списка в памяти

«Бесконечно» означает on-demand generation, а не создание тысяч упражнений:

- клиент держит небольшое окно текущих/следующих вопросов;
- следующий question запрашивается или выбирается после ответа;
- сервер/локальный selector хранит seed и session state;
- упражнения генерируются из проверенных templates и reviewed item bank;
- недавние IDs не повторяются слишком часто;
- память сессии ограничена;
- история попыток пишется порциями;
- при ручном завершении показывается summary;
- сессия может быть возобновлена после обрыва.

### Выбор тем

Экран темы должен показывать:

- название;
- раздел курса;
- mastery;
- последнюю практику;
- количество доступных шаблонов;
- статус teacher review;
- checkbox/toggle выбора.

Добавь команды:

- выбрать все доступные;
- снять выбор;
- выбрать слабые;
- начать.

Не используй только длинный список одинаковых карточек. На desktop допускается
двухколоночная компоновка, на mobile — плотный сканируемый список.

### Адаптивный selector

Вероятность темы зависит от:

- выбора пользователя;
- `next_review_at`;
- mastery;
- недавних ошибок;
- времени с последней практики;
- разнообразия exercise type;
- ограничения повторов одного objective подряд.

Формула должна быть объяснимой, вынесенной в config и покрытой тестами.
Случайность — с seed для воспроизводимости.

### Генерация упражнений

Не отправляй непроверенный текст LLM на каждый вопрос. Используй:

- reviewed static item bank;
- параметризованные templates;
- проверенные леммы и формы;
- morphology validator;
- curated distractor strategies.

Каждый сгенерированный instance должен пройти runtime validation:

- ответ существует;
- distractors отличаются;
- форма подтверждена;
- sourceRef известен;
- target objective совпадает;
- предложение не содержит placeholder;
- script соответствует режиму.

Если валидный instance построить нельзя, selector выбирает другой template и
логирует content diagnostic, но не показывает пользователю сломанное задание.

### Сессия тренировки

Хранить:

```text
sessionId
userId
mode
selectedObjectiveIds
seed
startedAt
lastActivityAt
answeredCount
correctCount
currentStreak
pendingExerciseId
status
```

Статусы:

- `active`;
- `paused`;
- `completed`;
- `expired`.

### Завершение

Пользователь всегда может нажать «Закончить тренировку». Показать:

- длительность;
- число ответов;
- точность;
- темы;
- mastery changes;
- типичные ошибки;
- рекомендованную следующую практику.

Бесконечная тренировка не должна засчитываться как финальная контрольная и не
должна автоматически открывать обязательные уроки без прохождения их
объяснений.

### Связь с прогрессом

- правильные ответы дают evidence для mastery;
- ошибки попадают в review queue;
- упражнения влияют на streak/XP;
- один и тот же replay не должен бесконечно фармить progress;
- server idempotency предотвращает двойное начисление;
- trainer history доступна пользователю;
- удаление аккаунта удаляет trainer sessions.

### UX

Во время тренировки используется тот же `ExerciseHost`, evaluator, feedback и
маскот, что в уроках. Не создавай второй несовместимый движок упражнений.

Отличия:

- нет общего lesson progress bar с концом;
- вместо него — счётчик сессии и текущая серия;
- CTA «Закончить» всегда доступен в меню;
- после ошибки можно кратко открыть правило;
- следующий вопрос не загружается с заметным пустым экраном.

### Тесты тренажёрки

- topic filtering;
- weak-topic weighting;
- seeded reproducibility;
- no immediate duplicates;
- bounded memory;
- invalid template retry;
- pause/resume;
- manual finish;
- idempotent scoring;
- mastery update;
- account deletion cascade;
- offline pending attempts.

## 17. Mastery model

Для небольшого клона не нужен сложный ML. Используй объяснимую модель:

- новая цель: 0;
- правильный ответ без подсказки повышает сильнее;
- правильный со второй попытки повышает меньше;
- ошибка снижает или увеличивает review urgency;
- старые знания со временем получают review due date;
- score ограничен диапазоном;
- completion урока и mastery темы — разные вещи.

Все коэффициенты вынести в config и покрыть unit tests.

Не заявлять научную точность, если используется простая эвристика.

## 18. Мотивационные механики

## 24. Управление состоянием

В проекте уже есть `provider`. Не добавляй новый state-management framework
без сильной причины.

Раздели:

- auth session state;
- course catalog/progress state;
- transient lesson attempt state;
- animation state;
- sync state.

`LessonController` должен быть тестируемым без WidgetTester:

- current exercise;
- selected answer;
- checked state;
- correctness;
- feedback;
- retry queue;
- score;
- next/finish.

Не выполнять API call из `build()`.

## 25. Сохранение незавершённого урока

Пользователь не должен терять попытку при:

- сворачивании приложения;
- web refresh;
- падении сети;
- случайном Back;
- обновлении токена.

Сохранять:

- lesson ID;
- content version;
- exercise order/seed;
- current index;
- ответы;
- retry queue;
- startedAt;
- elapsed active time;
- sync state.

При несовместимом content update показать понятное сообщение и безопасно
завершить/перезапустить попытку.

## 26. Миграция старого раздела

Текущий `GrammarCardsScreen` содержит темы и flip-карточки.

Сделай:

1. Новый route «Грамматика» ведёт в auth-aware course gate/path.
2. Старые подробные правила можно временно оставить как «Справочник» внутри
   курса, если они проверены по книге.
3. `GrammarScreen` из читалки остаётся.
4. Старые route names и imports удалить только после проверки usages.
5. Не переносить непроверенные старые объяснения в новые уроки автоматически.
6. При необходимости переименовать старый экран в
   `GrammarReferenceScreen`, чтобы различать курс и справочник.

## 27. Валидация курса

Создай CLI/build validator, который падает при:

- duplicate course/unit/lesson/exercise IDs;
- missing prerequisite;
- цикле prerequisites;
- пустом уроке;
- отсутствии правильного ответа;
- accepted answer вне token set;
- одинаковом correct и distractor;
- отсутствующем image/sprite asset;
- неверном sourceRef;
- неизвестном exercise type;
- непокрытом обязательном objective;
- финальной контрольной без покрытия unit;
- использовании draft content в production, если config это запрещает.

Validator должен выдавать путь до конкретного элемента.

## 28. Контентные distractors

Неправильные варианты должны быть педагогически осмысленными:

- форма другого лица;
- соседний падеж;
- неправильное управление;
- смешение `č/ć`;
- неверный порядок клитик;
- форма другой письменности только в script lesson.

Не использовать случайные бессмысленные строки. Distractor должен
диагностировать типичную ошибку.

Каждый distractor желательно маркировать:

```text
misconceptionId
feedbackKey
```

Так результат может объяснить конкретную ошибку.

## 29. Согласование с морфологическим движком

Используй `GrammarEngine` и `LexiconDb` как валидаторы/помощники, но книга и
reviewed course content имеют приоритет.

Добавь development tooling, которое:

- проверяет леммы;
- ищет формы в лексиконе;
- сравнивает feats;
- отмечает generated-only формы;
- выводит расхождения;
- не молча переписывает авторский ответ.

Если legacy CLASSLA baseline, новый Go-compatible NLP adapter, лексикон и
книга расходятся:

1. Зафиксируй конфликт.
2. Не выбирай ответ автоматически.
3. Пометь content item на teacher review.

## 30. Письменности

Сербский использует латиницу и кириллицу.

Course config должен явно определять:

- основную письменность урока;
- принимается ли вторая;
- показывается ли transliteration hint;
- проверяется ли конкретно владение письмом.

Нельзя автоматически превращать любой русский кириллический ответ в сербский.
Используй существующий `SerbianTransliteration` только там, где это
педагогически допустимо.

## 31. Изображения упражнений

Храни изображения отдельно от sprite animations:

```text
frontend/assets/course/images/
frontend/assets/animations/
```

Добавь в `pubspec.yaml` только необходимые каталоги.

Оптимизация:

- разумное разрешение;
- WebP/PNG/JPEG по содержанию;
- `cacheWidth`/`cacheHeight` там, где полезно;
- precache следующего изображения;
- не держать весь image course в декодированной памяти;
- error state;
- focal point.

Не использовать SVG-иллюстрации вместо предоставленных bitmap assets, если
пользователь дал изображения.

## 32. Аналитика обучения

Если добавляется analytics, она должна быть privacy-preserving и
конфигурируемой.

Полезные события:

- lesson_started;
- exercise_answered;
- hint_used;
- lesson_completed;
- lesson_abandoned;
- review_completed;
- exam_completed.

Не отправлять:

- пароль;
- access token;
- тексты личных книг;
- полный email в event properties;
- свободный пользовательский текст без необходимости.

Без настроенного analytics provider события можно хранить агрегированно на
сервере курса. Не подключай рекламный SDK.

## 37. Performance budgets

Цели:

- открытие карты не декодирует все sprite sheets и изображения курса;
- lesson загружает текущие и ближайшие assets;
- rebuild не пересоздаёт весь course model;
- animation не декодирует файл на каждом кадре;
- progress sync batching;
- список узлов builder-based;
- content JSON парсится один раз и кешируется;
- старые попытки пагинируются;
- web не вытягивает тексты всех книг;
- новый auth/course init не блокирует Dashboard.

Профилируй, а не только предполагай.

## 38. Security checklist

- password hash: Argon2id или актуальный эквивалент;
- generic login errors против user enumeration;
- rate limit;
- email normalization;
- refresh token hashing/revocation;
- HTTPS production;
- no secrets in Flutter;
- no tokens in logs/URLs;
- parameterized SQL/ORM;
- schema validation;
- account delete;
- auth dependency на progress endpoints;
- object ownership checks;
- CORS allowlist;
- CSP для web deployment, если доступно;
- dependency audit;
- backup/migration plan для production DB.

Не называй систему production-ready, пока эти пункты не реализованы и не
проверены.

## 41. Definition of Done

Задача выполнена только если:

1. Грамматика на главной открывает новый курс.
2. Guest видит auth gate, но продолжает пользоваться читалкой.
3. Можно зарегистрироваться, войти, выйти и восстановить session.
4. Аккаунты, сессии и progress хранятся в PostgreSQL, а не на эфемерном
   диске Space.
5. Есть versioned course, созданный на основе Markdown книги.
6. У каждого правила есть source provenance.
7. Все обязательные разделы, выделенные из книги, представлены полноценными
   уроками; первый vertical slice не остался единственным заполненным разделом.
8. Реализованы все четыре обязательных семейства:
   - sentence builder;
   - verb/noun ending;
   - image description;
   - letter unscramble.
9. Ответы проверяются детерминированно.
10. Ошибки объясняются.
11. Исходные PNG-кадры автоматически обработаны: непрозрачный фон удалён без
    повреждения персонажа, кадры стабилизированы и собраны в atlas.
12. Sprite-анимации Читавука работают из generated assets и manifest.
13. Reduced motion имеет fallback.
14. Course path и unlock logic работают.
15. Review queue работает.
16. «Тренажёрка» позволяет выбирать темы и бесконечно практиковаться без
    бесконечного потребления памяти.
17. Тренировка сохраняет попытки, mastery и корректно завершается вручную.
18. Финальная контрольная проверяет весь курс.
19. Результат показывает слабые темы.
20. Незавершённый урок восстанавливается.
21. Весь production backend написан на Go и не запускает Python.
22. Все необходимые legacy endpoints перенесены и прошли contract tests.
23. PostgreSQL migrations и backup/restore задокументированы и проверены.
24. Android/Windows/web не имеют платформенных импортов, ломающих сборку.
25. Старый grammar analysis в читалке работает через Go backend/fallback.
26. Тесты и сборки проходят.
27. Документация обновлена.
28. Нет известных пустых заглушек в основном user flow.

## Как использовать

1. Убедись, что Markdown книги Просвирниной доступен внутри рабочей области.
2. Положи исходные последовательности PNG-кадров Читавука с непрозрачным

4. Дай агенту доступ к репозиторию и возможность запускать Flutter, Go,
   Docker и PostgreSQL. Python нужен только временно для сравнения старого
   backend во время миграции.
5. Не проси его сразу генерировать весь учебный контент без промежуточной
   проверки первой темы преподавателем: сначала лучше подтвердить content
   schema, один unit и формат упражнений.
